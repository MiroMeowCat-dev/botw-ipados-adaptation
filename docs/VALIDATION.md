# 验证与性能结论

## 真机已确认

设备为 11 英寸 iPad Pro M5，iPadOS 27.0.1。用户已实际进入场景并控制林克；确认全屏黑边消失、背包自动 16:9 且退出恢复全屏、v7 切换更快；确认体感瞄准跟随 iPad 且方向正常。

v10 安装后用户确认：统一设置和虚拟手柄显示开关正常；隐藏手柄后设置入口仍可用；布局拖动后取消可恢复；体感开关、重新校准及背包自动切换均正常。系统设置里的入口隐藏开关已打包，但该单项没有收到明确真机验收反馈。Xbox 尚未连接实测，不归入通过项。

同身份覆盖更新时，检查了 15 个主数据分片、种子标识与 22 个存档/槽位文件的哈希；更新前存档/偏好备份总计 9,624,056 字节。个人备份和哈希逐文件列表未公开。没有完成全部剧情、全部菜单、神庙体感机关和长时热稳定性测试。

## 构建检查

历史 v10 三个模块严格警告编译通过、静态分析各零条诊断。主体完整 ZIP CRC 通过；主程序与 v9 相同，26 个无关条目保持原尺寸/CRC。个人签名时另核对了四个 Mach-O 的签名与内存权限；个人签名文件不发布。

| 检查 | 逻辑检查数 |
| --- | ---: |
| 背包检测 | 11 |
| 菜单状态机（30/60/120 Hz） | 38 |
| 体感坐标与样本有效性 | 34 |
| 触控几何边界 | 908 |
| 限帧策略 | 15 |

共 1006 个逻辑条件检查，**不是 1006 次真机测试**；几何测试也不代表 UIKit 真机行为全部覆盖。Objective-C 所有权检查源码保留，但纯 C 检查器不会在 Windows 主机运行 UIKit 测试。

归档时从整理后的源码重新编译三个模块，哈希均与真机已验收的 v10 模块完全一致，静态分析零诊断。新打包工具对私有固定 v9 输入生成的候选也通过完整 CRC、宿主不变及 26 个无关条目检查；不兼容输入被拒绝且没有产生输出。本次没有将重新打包的候选再安装到 iPad，归档验证与此前真机验收分别记录。

## 性能对照

v8 约相同场景、固定镜头的本地记录：

| 配置 | 帧耗时 p50 | GPU 耗时 | CPU replay / frame |
| --- | --- | --- | --- |
| 屏幕 MetalFX / 跟随游戏 | 23.50–24.04 ms | 17.33–17.58 ms | 5.655–5.879 ms |
| 屏幕普通放大 / 跟随游戏 | 21.71–21.90 ms | 17.34–17.40 ms | 6.061–6.074 ms |
| 旧显式 60 目标 | 33.38–33.41 ms | 连低 GPU 负载菜单也固定节奏 | 重复限帧被定位 |

前两个样本工作量约差 9%，热状态也不完全相同，不能把约 2 ms 差异全部归因于 MetalFX，更不能用 `1/p50` 宣称平均 FPS。GPU 本身约 17 ms 的时段已可能限制 60 帧预算。

v9 使用 display 呈现间隔后，恢复日志的最近三个 900 帧分段 p50 为 17.66 / 16.83 / 16.65 ms。它们不再呈现此前固定 33 ms 模式，但场景不受控，不能当成严格 v8/v9 加速比或稳定 60 帧证明。

## 曾出现的黄色提示

- `LSSupportsGameMode` 缺失：应用元数据声明问题，后来补入；不是内存泄漏提示。
- CPU encoding 占帧时间较高：CPU 在编码/提交绘制命令，不能据百分比推断整个 M5 CPU 利用率。尚未迁移全部渲染后端到 MTL4CommandBuffer。
- 多个相似 render pass：提示可能合并 pass / 减少 GPU 切换，需要后端分析；未完成通用合并优化。
- 编译若干 shaders：首次遇到管线可能卡顿，缓存后未必再次出现；未完成全部 MTL4Compiler 改写。

这些多为 Metal 性能建议，随场景、阈值和缓存出现。v10 默认关闭测试提示/HUD，让日常界面干净，并不等于消除了其指向的底层开销。iPad 公共性能 HUD 也不提供已校准的整机瓦数测量。

## 后续恢复开发的优先级

1. 先确认相同构建、存档/镜头、分辨率、热状态，再比较帧时间/GPU/CPU，保留原始私有日志。
2. 定位 render pass 与 CPU replay 实际热点，避免仅凭芯片型号或桌面 GPU 对比推断瓶颈。
3. 如需取消背包切换，从菜单裁切/布局及预览相机做专门适配，当前自动兼容仅为可靠折中。
4. Temporal / 插帧需要运动矢量、深度、历史帧及节奏链路，不是加一个开关即可。
